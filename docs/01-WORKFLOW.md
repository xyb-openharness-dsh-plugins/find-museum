# 从需求到可用工作台

## 1. 先明确边界

工作台承载业务与数据；DSH 提供模型、工具、权限和原生会话。不要先研究或改造全部 Desktop 源码。只读与自己接入有关的规范、接口类型和一个已验证例子。独立 dmg/exe 与插件 tgz 是不同交付范围。

目标用户、场景、核心流程、产出、离线/联网边界缺失时先澄清。已有对话明确过的内容直接继承，不要求重复填写。用模板 BRIEF 记录；业务未知时不照搬其他项目的页面结构。

## 2. 通过互动完善设计

先让模板就绪，再由 Agent 通过对话填写，明确区分“建议/待确认/已确认”；用户无需独自面对空白 SPEC 或 JSON 配置。每轮聚焦一个决策，继承已有回答。UI 优先选一个合适的专用技能共创可交互原型，实际预览后请开发者确认；数据同时比较 JSON、SQLite 与可选记忆混合方案。具体步骤见 [互动设计](07-INTERACTIVE-DESIGN.md)，可直接使用 [共创提示词](../prompts/DESIGN-WITH-ME.md)。

## 3. 盘点与冻结设计

确认 cwd、Git 分支与未提交修改、脚本、锁文件、目标 Desktop 版本/OS/架构。记录原型文件名、SHA-256 和确认日期。禁止在已确认 v3 上随手试改：新方案另存版本，旧版纳入 Git；浏览器另存文件夹作为恢复证据，不当作唯一备份。

从原型逐页列出“一级页→二级页→模块→字段→状态→点击→结果→回顾”。每个控件赋稳定 ID，如 `NUT-METRIC-FLIP`；功能表绑定 API、组件和验收证据。核对隐藏/折叠内容、配置弹窗、安宁/哀伤等子页，避免只按截图抄首页。

## 4. Spec 和实现次序

| 阶段 | 产物 | 进入下一阶段的条件 |
| --- | --- | --- |
| 需求/能力评估 | BRIEF、SPEC、布局 ADR、宿主能力矩阵 | 核心闭环与限制清楚 |
| 设计冻结 | 功能树、原型 hash、PARITY、token | 所有一级/二级页和动作可追踪 |
| 数据/API | 实体关系、表/迁移、读写合同、错误码 | UI 所需字段有来源；空/错误行为明确 |
| 接入基线 | 包四要素、健康接口、简单注册 | 能独立加载；无会话可用 |
| 共享 UI | 页面壳、卡片、图表、弹窗、建议入口 | 共享状态和尺寸有窄范围检查 |
| 完整业务单元 | 一个 Tab 的结构/数据/操作/状态 | 按该 Tab 验收，随后每 2–3 个关联 Tab 回归 |
| 里程碑 | 集成、包清单、版本、安装记录 | 从实际 tgz 在目标 Desktop 操作 |
| 交付 | ACCEPTANCE、README、变更记录、交接 | 未验证/限制明确；按授权推送/发布 |

契约冻结后，数据/API 与不共享文件的页面工作可并行；不要求每个小字段都完成一轮完整测试。多人/多 Agent 时先分文件与责任，最终归一到同一功能矩阵。

## 5. 省 token 的工作法

1. 用 `rg --files` 找文件名，读目录索引/标题，再按主题读取段落。不要让 Agent 每轮重读全部原型和数万行日志。
2. 历史先看 `git log --format=... -- <路径>`，再看有关提交的 `git show --stat`，最后只读目标文件 diff。版本号不是提交证据。
3. 一次维护短交接：当前版本/分支、已完成 ID、待办、真实失败、下一条命令和未验证事项；原始日志按需链接。
4. 日志保留错误附近 4000 字节，输出大小未知时按字节截断。构建示例：`set -o pipefail; npm run check 2>&1 | tail -c 4000`；PowerShell 使用本机等价机制记录真实退出码，不照抄 Bash 管道。
5. 同一事实只维护一个权威位置：功能状态在 TASKS，偏差在 PARITY，测试在 ACCEPTANCE。其余文档引用 ID，不复制多份“已完成”。

## 6. 日常完成单位

一次交付应是一个可复现的业务流程，如“文件导入→预览→解析→人工核对→指标更新→回顾”。提交前记录做了什么、证据、仍不支持什么。不要把“页面标题都出来了”写成全部 Tab 完成。
